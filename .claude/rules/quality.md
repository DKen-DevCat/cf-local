# Quality

レビュー観点で「設計の正しさ」と「スコープ管理」を見るためのルール。詳細は `CLAUDE.md` と `DESIGN.md` を参照。

## 設計判断

- DESIGN.md に書かれた判断からの逸脱は **コードを書く前にユーザー確認** が必要だった痕跡があるかを見る
- AWS / njs / Terraform の挙動について「たぶんこう」で書かれていそうな箇所はフラグする
- `cache_key` / TTL / cache invalidation のような微妙な領域はテストが先に存在するかを確認する（テストファースト）

## スコープ

- DESIGN.md の「やらない」リストにあるものを実装していないか
- 1 PR = 1 フェーズの 1 論理単位を超えて、関係ないリファクタが混ざっていないか
- セキュリティ機能（認証 / 認可 / 暗号化）は **このプロジェクトでは不要**。混入していたら不採用候補

## 抽象化

- 重複が 3 回未満で抽象化されていたら過剰抽象の疑い → 不採用候補
- ユーティリティ関数の追加は呼び出し元の数と複雑度を見る
- インターフェースは利用側にいくつ実装があるかを確認する（実装が 1 つだけなら早すぎる抽象化の疑い）

## エラー / panic / コメント

- 入力バリデーションは境界（HTTP ハンドラ / 設定ロード）でのみ。内部関数は信頼してよい
- エラーは握りつぶさない。`_ = err` / `// ignore` には強い理由が要る
- コメントは「なぜそうしたか」のみ。「何をしているか」のコメントは不要（命名で表現する）

## 依存

- 標準ライブラリで足りるなら新規ライブラリは追加しない
- 採用許可済み: `bbolt`, `aws-sdk-go-v2/service/cloudfront`
- 新規依存は go.mod に出ているか + PR 説明に判断理由が書かれているかを確認

## テスト

- 新規ロジックには `*_test.go` が同梱されているか
- テーブル駆動の name フィールドが具体的か（"case 1" のような無名は不採用候補）
- HTTP ハンドラのテストは `httptest` を使っているか

## 動作確認

- フェーズ完了時点で「実際に動かして確認できる」状態か
- 動かないコード（コンパイル通るが実行できない）が混入していないか
- 統合テストや α regression が必要なフェーズで `Test plan` セクションが PR 本文にあるか
