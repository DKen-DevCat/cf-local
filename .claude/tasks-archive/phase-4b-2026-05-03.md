## 引き継ぎ

- **`BL-OB1`** (新規): HTTP request log middleware。実機検証 G-1 で「想定外 API 呼び出しがないか log 確認」を間接指標に倒した経緯。observability + 将来 BL-NX2 stress test の request 追跡用途。phase-4c 仕上げ候補
- **`BL-W1` / `BL-W2`**: middle / suffix wildcard サポート。AWS 厳格 prefix match のみ実装したため、いずれも phase-4b で 400 InvalidArgument で reject。AWS 仕様拡張 or 強い要望時に再評価
- **`BL-IV1`**: Invalidation worker の並列度向上 (現状 serial 1 goroutine)。phase-4c で性能要件出たら
- **`BL-IV2`**: crash recovery で `InProgress` の re-execute (現状は起動時 `Completed` 強制遷移)。phase-5
- **`BL-IM1`**: managed CachePolicy `IllegalUpdate` の AWS 正規エラーコード確認 (phase-4a 4a-9 未確認継続)
- **`BL-NX1` / `BL-NX2` / `BL-NX3` / `BL-PP1` / `BL-LD1`**: いずれも phase-4a からの繰越し、phase-4b スコープ外。phase-4c 以降で再評価
- **`BL-RV1` (rules 領域別分割)**: phase-4b の `/phase-review` で領域別の精度問題は顕在化せず (PR #9 で `code-reviewer` agent が 3 並列で安定動作)。現時点で分割不要、`code-reviewer.md` の領域指示で十分。phase-4c 以降で再観測候補
- **`BL-RV2` (`/phase-review` 軸 (4) 公式ドキュ準拠の効き再観測)**: phase-4b では `/security-review` 0 件 + `/review-diff` 2 件で完結し、軸 (4) の独立起動は実施せず。AWS XML 互換は外部仕様 doc が薄く軸 (4) との相性が悪い傾向は継続。phase-5 OSS 公開準備で外部依存が増える際に再評価
