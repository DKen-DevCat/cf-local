# Phase 2: TTL正確化

## 目的

CloudFront と同じ TTL 決定ロジックを njs で実装し、`X-Accel-Expires` ヘッダで nginx に動的に伝える。Phase 1 で「cache key で識別された slot」の中身を、上流の `Cache-Control` に応じて適切な期間だけ保持できるようにする。

DESIGN.md §4.2 の 3 ケース:

| ケース | 条件 | 結果 |
|---|---|---|
| 1 | `Cache-Control` に `no-store` / `no-cache` / `private` のいずれか | TTL = MinTTL (MinTTL=0 → 結果的にキャッシュしない) |
| 2 | `Cache-Control: max-age=N` がある | TTL = clamp(N, MinTTL, MaxTTL) |
| 3 | `Cache-Control` がない | TTL = DefaultTTL |

`s-maxage` は `max-age` より優先される。

### 全体アーキテクチャ上の位置づけ

DESIGN.md §3.1 の Data Plane 強化フェーズの第二弾。Phase 1 の cache key (`cache_key.js`) と **直交**するレイヤー: cache key は「どの slot か」を決め、TTL は「その slot を何秒持つか」を決める。既存の `cache_key.js` には触らずに `cache_control.js` / `ttl.js` を追加する形。

## 着手前相談ポイント (要議論)

実装に入る前に以下 3 点をユーザと合意する:

| # | 相談点 | 仮の方針 |

## 2-1 spike 結果 (nginx 1.27.5 / njs 0.8.10)

**重大な発見**: DESIGN.md §4.2 の前提「njs から X-Accel-Expires を inject して proxy_cache に伝える」が **1-hop 構成では成立しない**。`js_header_filter` は cache 判定後に実行されるため、`r.headersOut['X-Accel-Expires']` の書き換えは proxy_cache の TTL 決定に届かない。

### 実験結果サマリ

`nginx/njs/spike/ttl_probe.js` を `js_header_filter` に登録し、`X-Test-TTL` リクエストヘッダで X-Accel-Expires を任意値に inject。`/favicon.ico` を upstream として 4 ケース測定:

| 構成 | TTL inject | 期待挙動 | 実測 | 判定 |
|---|---|---|---|---|
| 1-hop `/_ttl_probe` | TTL=5 | t=7 で MISS | t=7 でも **HIT** | ❌ injection 効かず |
| 1-hop `/_ttl_probe` | TTL=0 | 毎回 MISS | 2 回目以降 **HIT** | ❌ 同上 |
| 2-hop `/_2hop_outer` (proxy_pass → inner) → `/_2hop_inner` (`js_header_filter` → origin) | TTL=3 | t=4+ で EXPIRED/MISS | MISS → HIT → **EXPIRED** | ✅ injection 効く |
| 2-hop | TTL=0 | 毎回 MISS | **MISS 永続** | ✅ |
| 2-hop | (header 無し) | proxy_cache_valid 1m fallback | MISS → HIT (within 1m) | ✅ |

### なぜ 2-hop で動くか

nginx の proxy_cache は **upstream レスポンスを受け取った時点**で X-Accel-Expires を読んで TTL を決定する。`js_header_filter` はその後の output filter chain で走るので、1-hop では cache 判定に間に合わない。

2-hop パターンでは:
- 内側 (`/_2hop_inner`) が実 origin を proxy_pass し、自身の output filter chain で `js_header_filter` が走り X-Accel-Expires を inject
- 外側 (`/_2hop_outer`) は内側を upstream として `proxy_pass http://self/_2hop_inner` で受け取る。**外側視点では「内側が出した最終ヘッダ」がそのまま upstream のヘッダ**として認識される
- 外側の proxy_cache は内側出力に乗っている X-Accel-Expires を読んで TTL を決定する → 動く

### Phase 2 アーキテクチャへの含意

DESIGN.md §4.2 を維持するには **2-hop パターンの採用が必須**。1-hop で TTL 動的注入する設計は技術的に不可能 (公式ドキュメント上も明示の代替フックなし)。

追加コスト:

- 各 cacheable location に **outer / inner ペア** が必要
- `upstream self { server 127.0.0.1:8080; }` を nginx.conf に常設
- 内側 location の URL prefix (`/_cf_inner_*` 等) の予約と衝突回避
- TCP self-loop による微小レイテンシ (実測 sub-millisecond)
- Phase 1 の `/` location も Phase 2 で 2-hop に refactor する必要あり (現状 1-hop なので TTL 動的注入できない)

代替案 (2-hop を採らない場合):

| 代替案 | できること | 失うもの |
|---|---|---|
| 上流 Cache-Control を **honor** (`proxy_ignore_headers` から外す) + binary `proxy_no_cache` | 上流の max-age をそのまま TTL に | MinTTL/MaxTTL clamp、policy 単位の TTL 上書き |
| 静的 `proxy_cache_valid` のみ (njs での TTL 計算を諦める) | 単純 | DESIGN.md §4.2 ケース 1/2 の動的判定すべて |
| Go control plane 経由で X-Accel-Expires 注入 (Phase 4-A 以降) | DESIGN.md 維持 | Phase 2 完了時期が大幅に後ろ倒し |

### 結論

**2-hop パターンを採用**して本フェーズを進める方向を推奨。代替案は Phase 2 のゴール (CloudFront 互換 TTL 3 ケース + s-maxage + clamp) を放棄することになる。spike 完了時点で要ユーザ承認。

### probe.js / spike infra の扱い

`nginx/njs/spike/ttl_probe.js` は再現性のため残す。冒頭コメントに 2-hop / 1-hop 両方の再実行手順を記載済。`nginx.conf` 側の `js_import ttl_probe` / `upstream self` / spike 用 location 群は 2-1 完了に合わせて畳んだ。

## 2-2 アーキテクチャ確定 (2-hop 採用)

2-1 spike で 1-hop の不可が判明したため、Phase 2 は **2-hop パターン**で進める。本節で確定したもの:

### nginx.conf 2-hop レイアウト

```nginx
upstream origin {
    server host.docker.internal:3000;
}
upstream self {
    server 127.0.0.1:8080;   # Phase 4 以降で unix socket 化検討
}

# js_set は http レベル
js_set $cf_cache_key  ck.forNginx;
js_set $cf_policy_id_for_inner  ck.policyIdFromInnerUri;  # /_cf_inner_<id>/... から id 抽出

# (...)

server {
    listen 8080;

    # /_cache_key_test など Phase 1 既存の test endpoint は維持

    # Outer: cache 層 (cache_key 計算 + cache 判定)
    location / {
        set $cf_policy_id "default";
        proxy_cache cf_cache;
        proxy_cache_key $cf_cache_key;
        proxy_cache_valid 200 86400s;          # case 3 (no Cache-Control) の DefaultTTL fallback
        proxy_cache_valid 404 10s;
        proxy_ignore_headers Set-Cookie Vary;  # Cache-Control は inner で X-Accel-Expires に変換するので外側でも ignore してよい
        add_header X-Cache-Status $upstream_cache_status always;
        add_header X-Cache-Key    $cf_cache_key          always;
        proxy_pass http://self/_cf_inner_default$request_uri;
    }

    # Inner: TTL 注入層 (Cache-Control パース → X-Accel-Expires)
    location /_cf_inner_default {
        # 外部から直接叩かれないよう 127.0.0.1 限定 (unix socket 化までの暫定)
        allow 127.0.0.1;
        deny all;
        set $cf_policy_id "default";
        js_header_filter ttl.computeAndInject;
        proxy_pass http://origin/;             # `/_cf_inner_default/<x>` → `/<x>` に rewrite
    }
}
```

設計判断:

| 項目 | 決定 | 代替案 (将来) |
|---|---|---|
| self-loop transport | **TCP via `upstream self`** | unix socket (1 server block 増、Phase 4-A で再評価) |
| inner 保護 | **`allow 127.0.0.1; deny all;`** | unix socket 化、または `internal;` (現状 proxy_pass 経由を弾く副作用あり、不可) |
| inner URL prefix | **`/_cf_inner_<policy_id>`** で予約 | Phase 3 の Go テンプレート生成で動的命名 |
| 既存 `/` location | **本フェーズで 2-hop 化 (refactor)** | — |
| `proxy_pass http://origin/` の trailing slash | **必須**: `/_cf_inner_default/<x>` → `/<x>` に rewrite | — |
| 1 policy = 1 inner location | Phase 2 では `default` のみ refactor (現状 `/` だけが cacheable location) | Phase 3 で多 policy → 多 inner location 自動生成 |

### TTL 決定ロジック (`ttl.compute(parsedCC, policyTtl)`)

```javascript
function compute(cc, p) {
    // case 1: no-store / no-cache / private → MinTTL (0 で実質キャッシュしない)
    if (cc.noStore || cc.noCache || cc.private) return p.min_ttl;

    // case 2: max-age=N (s-maxage が優先)
    const explicit = cc.sMaxage !== null ? cc.sMaxage : cc.maxAge;
    if (explicit !== null) {
        return Math.max(p.min_ttl, Math.min(p.max_ttl, explicit));
    }

    // case 3: Cache-Control 不在 → DefaultTTL
    return p.default_ttl;
}
```

戻り値は **整数秒**。`0` のとき `X-Accel-Expires: 0` を出す → 2-1 spike で確認済の通り proxy_cache は cache しない。

### Cache-Control パーサー (`cache_control.parse(headerValue)`)

スコープは DESIGN.md §4.2 が言及する 5 directive のみ。それ以外の directive は無視する (Phase 4 で互換性が必要になったら拡張)。

| directive | 出力フィールド |
|---|---|
| `no-store` | `noStore: true` |
| `no-cache` | `noCache: true` |
| `private` | `private: true` |
| `max-age=N` | `maxAge: N` (整数 0 以上) |
| `s-maxage=N` | `sMaxage: N` (整数 0 以上) |

戻り値:

```javascript
{ noStore: false, noCache: false, private: false, maxAge: null, sMaxage: null }
```

### policy schema 拡張

Phase 1 の 4 policy (`default` / `with-session` / `with-locale` / `_test-empty-cookie`) に以下 3 フィールドを追加。CloudFront `CachePolicy` 互換のデフォルト値:

| field | 型 | デフォルト | 意味 |
|---|---|---|---|
| `min_ttl` | int (秒) | `0` | case 1 (no-cache 系) で適用される TTL |
| `max_ttl` | int (秒) | `31536000` (1 年) | case 2 max-age=N の上限 |
| `default_ttl` | int (秒) | `86400` (1 日) | case 3 (Cache-Control 不在) で適用 |

backward compat: 読み込み時に欠落していればデフォルトで埋める (`getPolicyTtl(policy)` 経由)。`policies.json` 自体は本フェーズで全 policy に explicit に書き込む方針。

### inner の `js_header_filter ttl.computeAndInject` (実装スケッチ)

```javascript
import cache_control from 'cache_control.js';
import ttl from 'ttl.js';
import ck from 'cache_key.js';   // getPolicy / getPolicyTtl の再利用

function computeAndInject(r) {
    const policy = ck.getPolicy(r.variables.cf_policy_id);
    const policyTtl = ck.getPolicyTtl(policy);             // 新設
    const ccRaw = r.headersOut['Cache-Control'];
    const cc = cache_control.parse(ccRaw);
    const seconds = ttl.compute(cc, policyTtl);
    r.headersOut['X-Accel-Expires'] = String(seconds);
}
```

注: `r.headersOut['Cache-Control']` は upstream (origin) のレスポンスヘッダを参照する (`js_header_filter` 実行時点で原ヘッダが入っている)。inject した `X-Accel-Expires` が outer 側 proxy_cache の判定に使われる (spike で実証済み)。
