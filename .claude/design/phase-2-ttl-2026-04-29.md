# Phase 2: TTL正確化

## 目的

CloudFront と同じ TTL 決定ロジックを njs で実装し、`X-Accel-Expires` ヘッダで nginx に動的に伝える。Phase 1 で「cache key で識別された slot」の中身を、上流の `Cache-Control` に応じて適切な期間だけ保持できるようにする。

DESIGN.md §4.2 の 3 ケース:

| ケース | 条件 | 結果 |
|---|---|---|
| 1 | `Cache-Control` に `no-store` / `no-cache` / `private` のいずれか | TTL = MinTTL (MinTTL=0 → 結果的にキャッシュしない) |
| 2 | `Cache-Control: max-age=N` がある | TTL = clamp(N, MinTTL, MaxTTL) |
| 3 | `Cache-Control` がない | TTL = DefaultTTL |

`s-maxage` は `max-age` より優先される。

### 全体アーキテクチャ上の位置づけ

DESIGN.md §3.1 の Data Plane 強化フェーズの第二弾。Phase 1 の cache key (`cache_key.js`) と **直交**するレイヤー: cache key は「どの slot か」を決め、TTL は「その slot を何秒持つか」を決める。既存の `cache_key.js` には触らずに `cache_control.js` / `ttl.js` を追加する形。

## 着手前相談ポイント (要議論)

実装に入る前に以下 3 点をユーザと合意する:

| # | 相談点 | 仮の方針 |
|---|---|---|
| A | `Cache-Control` パースの厳密さ (`s-maxage` / `no-cache` / 複数ディレクティブ重複) | 必要 directive (`max-age` / `s-maxage` / `no-store` / `no-cache` / `private`) のみ最小実装、その他は無視 |
| B | `X-Accel-Expires` の挙動確認 (TTL=0 を渡したとき "キャッシュしない" になるか "0 秒キャッシュ" になるか) | 2-1 spike で実機確認、必要なら `proxy_no_cache` 変数を `js_set` で立てる |
| C | TTL=0 のときキャッシュしない実装手段 | B の spike 結果次第。`X-Accel-Expires: 0` で済めばそのまま、ダメなら `proxy_no_cache` 経路 |

加えて、Phase 1 code-review で「Phase 2 着手前」と判定した B 優先 hardening 2 件を本フェーズの冒頭サブタスク (`2-0a` / `2-0b`) として組み込む方針:

- **concern #4** (`fs.readFileSync` の safe-default 化): `cache_key.js` の policies.json load が malformed JSON / missing file 時に worker 起動を止めない
- **concern #6** (α テスト silent skip 解消): 統合テストの origin 不在時を fail or 自動 mock origin 起動に切替

これらは TTL ロジックと直接関係ない hardening だが、本フェーズで `policies.json` schema 拡張 (`min_ttl` / `max_ttl` / `default_ttl` 追加) と mock origin 整備 (TTL の α テストに必要) を**どうせ触る**ので、独立した「Phase 1.x」を切らずに本フェーズで吸収する。

## 実装方針

### 共通方針

- DESIGN.md §4.2 の 3 ケース + `s-maxage` 優先規則をそのまま素直に実装。早めに最適化しない
- `cache_control.js` (パーサ) と `ttl.js` (TTL 決定) を分離。前者は string → object、後者は (parsed cc, policy ttl 設定) → 数値 + flag
- 2-1 の spike を Phase 1 と同様に最優先で実機検証。`X-Accel-Expires` の挙動はドキュメントだけでは確信が持てない領域 (CLAUDE.md「推測で進めない」)
- `cache_key.js` には触らない。policies.json schema 追加で読むフィールドが増えるだけ

### TDD

- 2-3 / 2-4 はテストファースト。red → green の 2 段コミット (Phase 1-3 と同じパターン)
- ケース表を spec として先に固定: 各 `Cache-Control` 入力に対して期待 (parsed object, ttl, no-cache flag) を表で書いて回す

### policy schema 拡張

`policies.json` に以下 3 フィールドを追加:

```json
{
  "default": {
    "headers": {...},
    "cookies": {...},
    "query_strings": {...},
    "accept_encoding_normalize": true,
    "min_ttl": 0,
    "max_ttl": 31536000,
    "default_ttl": 86400
  }
}
```

CloudFront `CachePolicy` の隣接フィールドに対応。Phase 1 の whitelist 系とは独立。`_test-empty-cookie` policy にもデフォルト値を入れて互換維持。

## テスト方針

- **(β) 単体**: `cache_control.parse(input)` / `ttl.compute(parsed, policyTTLs)` を pure function として直接 table-driven。Phase 1 と同じく `/_cache_key_test` 風の `js_content` endpoint で expose して Go から table-driven に叩く。`/_ttl_test` を新設
- **(α) 統合**: 2-0b で mock origin (`tests/integration/testserver/`) を立てて `Cache-Control` パターン別に HTTP リクエストを投げ、`X-Cache-Status` と HIT 維持時間を検証
- ケース網羅: `no-store` / `no-cache` / `private` × MinTTL / `max-age=N` × clamp 上下限 / `s-maxage=N, max-age=M` 優先 / Cache-Control 不在 → DefaultTTL
