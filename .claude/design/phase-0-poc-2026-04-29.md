# Phase 0: PoC

このフェーズは「最初の一歩」。完璧を目指さず、**動くものを作って実際に触る**ことを最優先する。Phase 1以降の詳細設計は、ここで得た学びを元に行う。

## 目的

nginx を Next.js（または任意の origin）の前段に置き、固定 config でキャッシュが動く最小構成を作る。**「キャッシュ挙動の検証」というプロジェクトの主目的が、この時点で限定的にでも体験できる**状態を目指す。

具体的なコアバリュー（マイルストーン M1）:

- nginx Dockerfile / nginx.conf / docker-compose の叩き台が想定どおり動くことを実機（ローカル開発機）で確認する
- Phase 1 以降に積み増す njs / X-Accel-Expires / ngx_cache_purge の前提となる **動く基盤** を確立する
- 動かしてみて初めて見える nginx / docker-compose の制約・はまりどころを Phase 1 設計に反映する材料にする

### 全体アーキテクチャ上の位置づけ

DESIGN.md §3.1 の Control Plane / Data Plane 分離のうち、**Phase 0 では Data Plane (nginx) のみを立ち上げる**。Control Plane (Go) は Phase 4-A から、Lambda@Edge 連携の edge-proxy (Go) は Phase 4-D から構築する。Phase 0 〜 Phase 3 までは固定 config + JSON 設定ファイル方式で Data Plane だけを段階的に強化する。

## 実装方針

### 0-1. nginxイメージの選定

DESIGN.md §3.2 で nginx を採用した決め手は次の 4 機能。Phase 0 時点ではどれも使わないが、後続フェーズで確実に必要になる:

| 機能 | 必要になる Phase | 用途 |
|---|---|---|
| njs (NGINX JavaScript) | Phase 1 | cache key 動的計算 |
| `X-Accel-Expires` | Phase 2 | TTL の動的注入 |
| `ngx_cache_purge` | Phase 3 | path 単位の invalidation |
| `ngx.fetch` (njs) | Phase 4-D | edge-proxy への HTTP 呼び出し |

候補:

- `nginx:1.27-alpine` + njsモジュール追加（apkで `nginx-mod-http-js`）
- `openresty/openresty:alpine` （njs, lua, cache_purge全部入り）
- カスタムビルド（最終手段）

**Phase 0 の方針（決定）**: 既存の叩き台どおり `nginx:1.27-alpine` 素のままで進める。njs / ngx_cache_purge 対応版への切替判断は **Phase 1 冒頭で行う**（実装着手前に Web 検索で公式イメージ事情を確認してから決定）。Phase 0 完了条件には image 切替は含まない。

### 0-2. nginx.conf 最小実装のポイント

- `proxy_cache_valid 200 1m` でとりあえず1分キャッシュ
- `X-Cache-Status` でキャッシュヒット/ミスを観察できるように
- `Host` ヘッダーをoriginに渡す（Next.jsのroutingが正しく動くため）
- Next.js起因でキャッシュが効かない場合は `proxy_ignore_headers Cache-Control Set-Cookie;` で一時回避（Phase 2で正規対応）

### 0-3. docker-compose.yml の注意点

- `extra_hosts: "host.docker.internal:host-gateway"` はLinux必須、macOS/Windowsでは無視されるが書いて問題ない
- `nginx-cache` ボリュームを永続化すると、再起動でキャッシュが残って検証しにくいことがある。状況に応じて `docker compose down -v` で消す

### 0-4. 動作確認手順

```bash
# 1. originを別途起動（例: Next.js）
cd <your-nextjs-project>
npm run dev   # 3000番で起動

# 2. cf-local起動
cd <cf-local>
docker compose up -d

# 3. 検証パスを決める: nginx.conf は proxy_cache_valid 200 1m なので、
#    origin が 200 を返す path を選ぶ。auth 付きの Next.js などは /
#    がリダイレクトを返すので注意（事前に origin 直で curl -sI して確認）。
#    zsh で ? を含む URL は "..." で囲むこと。
URL="http://localhost:8080/"   # 必要に応じて 200 が返る path に変更

# 4. 1回目: MISSのはず（同時に HTTP 200 も確認できる）
curl -sI "$URL" | grep -E "^(HTTP|X-Cache-Status)"
# HTTP/1.1 200 OK
# X-Cache-Status: MISS

# 5. 2回目: HITのはず
curl -sI "$URL" | grep -E "^(HTTP|X-Cache-Status)"
# HTTP/1.1 200 OK
# X-Cache-Status: HIT

# 6. ブラウザで確認
open "$URL"
```

**注意**: 同じ URL を 3 で warm-up すると 4 で MISS にならない。検証は 1 回目アクセスから始めること。`docker compose down -v` で cache volume を消せば再検証可能。

## 既知のはまりどころ

### macOSとLinuxで host.docker.internal の挙動が違う

- macOS / Windows: 標準で動く
- Linux: `extra_hosts` で `host-gateway` にマップする必要

### Next.jsのCache-Controlがproxy_cacheに影響する

Next.jsはデフォルトで `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` を返すことがある。これだとproxy_cacheがキャッシュしない。

Phase 0では `proxy_ignore_headers Cache-Control;` を加えてとりあえず無視する。Phase 2で正しいTTL決定ロジックに置き換える。

### X-Cache-Status が BYPASS になる

クライアントが `Cache-Control: no-cache` を送っている可能性。ブラウザのSuper Reload（Shift+Cmd+R）等。`proxy_cache_bypass` を意図的に設定していなければ大丈夫だが、原因不明の場合は `curl` で再確認。

### キャッシュが残ってて挙動が再現できない

- `docker compose down -v` でボリューム削除
- または `docker compose exec nginx rm -rf /var/cache/nginx/*` で中身だけ削除
