# Phase 4c: 仕上げ

## 目的

phase-4a/4b で動作するようになった Terraform 連携 + Invalidation API を、**他人が触っても破綻しないライン**まで仕上げる。M3 達成 (= OSS β 候補) のためのフェーズ。

具体的には以下 3 軸の品質向上:

1. **API 互換性**: ResponseHeadersPolicy 対応 + AWS 互換エラー形式
2. **観測性**: HTTP request log middleware + 構造化ログ
3. **基盤の堅牢化**: inner location の unix socket 化 + stress test ベースライン取得

## スコープ

### kickoff 前相談で確定した方針

| 項目 | 決定事項 | 根拠 |
|---|---|---|
| **A-1 エラー互換レベル** | 中程度 (CloudFront `<ErrorResponse>` 形式 + 主要 Code) | AWS SDK / Terraform Provider が parse できるレベル。完全互換 (内部コード一致) は非現実的 |
| **A-2 ログフォーマット** | `log/slog` で人間可読 default + `CF_LOCAL_LOG_FORMAT=json` で JSON | dev は人間可読、CI / 観測ツール連携は JSON。両対応はほぼ無料 |
| **A-3 デバッグ UI** | 作らない (out) | ログ整備で十分。UI は OSS 公開後の v0.2 候補 |
| **D ResponseHeadersPolicy** | `CustomHeadersConfig` + `CorsConfig` のみ | ローカル開発で頻出する 2 系統に絞る。残り 3 系統 (Security / ServerTiming / RemoveHeaders) は積み |

### 実装しない（積みタスクで保留）

| ID | 内容 | 理由 |
|---|---|---|
| BL-IV1 | Invalidation worker 並列度向上 | 性能要件未発生。ベースライン (4c-8) 取ってから判断 |
| BL-PP1 | PathPattern 拡張 (suffix/middle/exact wildcard) | 仕様調査コスト高。要望出てから |
| BL-NX3 | rename 順序 race の staging dir 化 | 実機問題が再発していない |
| BL-IV2 | crash recovery で `InProgress` re-execute | phase-5 OSS 公開時に判断 |
| BL-W1 / BL-W2 | Invalidation middle / suffix wildcard | AWS 仕様外。要望出てから |
| ResponseHeadersPolicy 残り 3 系統 | SecurityHeaders / ServerTiming / RemoveHeaders | ローカル用途で出番が少ない |

## 実装方針

### コミット粒度（1 機能 1 コミット）

1. ResponseHeadersPolicy schema + store + CRUD API（4c-1）
2. nginx.conf renderer に `add_header` 注入（4c-2）
3. AWS 互換エラー形式の共通ヘルパー + 既存ハンドラ移行（4c-3, 4c-4）
4. slog 採用 + HTTP request middleware（4c-5）
5. 既存 log.Printf を slog に置換（4c-6）
6. nginx.conf inner location の unix socket 化（4c-7）
7. stress test 追加 + 結果記録（4c-8）
8. Go loader sanitize（4c-9）
9. `docs/limitations.md` 完成（4c-10, 4c-11）

### TDD 対象

- AWS 互換エラー形式 (4c-3): XML マーシャリングの形が AWS と一致するかを golden file テストで担保
- ResponseHeadersPolicy renderer (4c-2): 既存の renderer golden file テストパターンを踏襲
- log middleware (4c-5): http handler にラップしてアサート

### リスク

- **4c-7 unix socket 化**: docker-compose で named volume 経由で socket を share する方式が必要。コンテナ間で `/run/...` を共有できるか実機検証が要る。最悪 abstract socket か TCP のままで unix domain socket 化を諦める fallback あり
- **4c-8 stress test**: vegeta を CI で回すかは未決。ローカル手動 + 結果を limitations.md に記載でも可
- **4c-3 エラー Code 一覧**: AWS SDK Go v2 の `cloudfrontTypes` を grep して正規 Code 名を確認。誤字でテスト落ちると地味に痛い
